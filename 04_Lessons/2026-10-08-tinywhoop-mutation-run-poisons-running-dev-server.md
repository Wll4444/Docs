# Прогон мутаций при запущенном dev-сервере Vite отравляет сервер: файлы на диске чистые, а он отдаёт мутанта, и следующий харнесс меряет его

**Что было.** `mutate.mjs` пишет мутацию в рабочее дерево и восстанавливает файл байт в байт; с `--with="true"` (проверка, что
все правки ещё применяются) — за миллисекунды. Рядом работал `vite` на :5173 — его же переиспользует `npm run shot`. Наблюдатель
Vite восстановления пропустил: на диске `debug.ts` и `FpvCamera.tsx` были чистыми, а сервер отдавал мутантов P1 и C1
(`curl :5173/src/dev/debug.ts` → `return q.get("debug") === "1";`). Следующая перезапись калибровки упала строка за строкой: панель
leva под `?e2e=1&debug=1`, горизонт на −212.49 px, «0 flights counted». Те же симптомы, что у мутаций, — на чистом дереве. После
перезапуска сервера всё прошло. Юниты (Vitest читает файлы сам) этого не видят никогда.

**Почему важно другим.** Каждый наследник Template держит dev-сервер открытым, пока играет человек или пока агент снимает
кадры, а мутационные прогоны идут в той же сессии. Отравленный сервер не падает и не предупреждает: он даёт уверенный красный
прогон на исправном коде (агент ищет дефект, которого нет) — или, хуже, зелёный на мутанте, если мутант совпал с ожиданием.

**Как применить.** `mutate.mjs` отказывается стартовать, если на порту dev-сервера кто-то отвечает (TinyWhoopPlayground,
`scripts/mutate.mjs`, этап 4d); без сервера `npm run shot` поднимает свой на каждую проверку и читает файлы как есть. После
любой правки файлов в обход редактора (скрипт, `git checkout`) перед замером харнессом — перезапустить сервер, а не верить
наблюдателю.
