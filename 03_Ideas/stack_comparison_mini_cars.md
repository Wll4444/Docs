# ⚖️ Сравнение стека: R3F/Rapier vs Godot 4
## Для проекта «Мини машинки в пустыне»

Точечное сравнение под конкретный capstone-проект, а не общая оценка стеков. Полное описание идеи — в `mini_cars_in_deser.md`.

---

## 📊 Сравнительная таблица

| Система | R3F + Rapier (текущий стек) | Godot 4 | Комментарий |
|---|---|---|---|
| **Vehicle physics** | Raycast vehicle controller собирается вручную поверх `RigidBody` — подвеска, сцепление, распределение тяги пишутся с нуля | `VehicleBody3D` из коробки — колёса, подвеска, сцепление настраиваются параметрами узла | 🟢 Заметное преимущество Godot: главный риск проекта закрывается готовым инструментом, а не неделями тюнинга своего контроллера |
| **Процедурный террейн** | Heightmap-меш + trimesh-коллайдер собирается вручную (генерация геометрии, нормали, LOD) | Нет полноценного встроенного terrain-инструмента в 4.x «из коробки», нужен аддон (напр. Terrain3D) | 🟡 Ничья со сдвигом в пользу R3F — там хотя бы полный контроль над своей реализацией, а не зависимость от стороннего аддона |
| **LOD и производительность больших карт** | Ручная реализация (chunking, frustum culling через drei-хелперы) | Встроенные механизмы виден-невидим, occlusion culling более зрелые в редакторе | 🟢 Небольшое преимущество Godot за счёт зрелости движка на больших сценах |
| **Модульная кастомизация машины (hot-swap мешей)** | Компонентная замена мешей через React-стейт — естественно для декларативного подхода | Замена узлов/мешей в Scene Tree через код или сигналы — тоже просто, но менее декларативно | 🟢 Небольшое преимущество R3F — это именно то, в чём сильна декларативная модель React |
| **Мини-система строительства (мост, брёвна)** | Ручная логика: drag-and-place + проверка через физические тела/сенсоры | Area3D + сигналы делают проверку "что-то легло на зону" чуть compact-нее | 🟡 Ничья, обе реализуемы примерно с одинаковыми трудозатратами |
| **AI/логика препятствий-«монстров» (без боя)** | Пишется вручную (стейт-машина в JS/TS) | То же самое вручную (GDScript), либо NavigationAgent3D для обхода препятствий, если понадобится pathfinding | 🟢 Небольшое преимущество Godot, если обход станет более сложным, чем «просто объезжай» |
| **AI-ассистированная разработка (MCP)** | Уже отработанный workflow с Claude в этом чате, привычные паттерны (инкрементальная сборка) | MCP-серверы есть (см. `godot_ai_stack.md`), но опыта меньше — придётся заново нарабатывать паттерны | 🟢 Преимущество R3F за счёт уже накопленного опыта |
| **Web-доставка (ссылка, без установки)** | Нативный веб — единственная целевая платформа, ничего не экспортируется дополнительно | HTML5/WASM-экспорт работает, но исторически тяжелее по размеру билда и времени загрузки, чем нативный R3F-проект | 🟢 Преимущество R3F — это твой заявленный приоритет («мобильный веб может проседать» уже учтено в ТЗ) |
| **Мультиплатформенность (desktop/mobile нативно)** | Требует обёртки (Capacitor/Tauri), если вообще понадобится | Единая кодовая база сразу под Windows/Linux/macOS/Android/iOS/Web | 🟢 Преимущество Godot, но нерелевантно, если цель — именно браузерная игра |
| **Blender-пайплайн для ассетов апгрейдов** | glTF/GLB импортируется в R3F без доп. шагов | glTF импортируется в Godot тоже без доп. шагов, тот же паттерн, что уже опробован с домом | 🟡 Ничья — оба варианта одинаково хорошо стыкуются с уже отработанным Blender-workflow |
| **Порог входа / переиспользование текущих знаний** | Ты уже владеешь стеком, весь опыт Рубика/будущих проектов переносится напрямую | Новый язык (GDScript), новая парадигма (Scene Tree вместо JSX), кривая обучения с нуля | 🟢 Существенное преимущество R3F — не приходится тратить время на освоение движка параллельно со сложным проектом |

## 🎯 Итоговая оценка по строкам

- **Явные победы Godot:** vehicle physics (главный технический риск проекта!), LOD/производительность больших карт, мультиплатформенность.
- **Явные победы R3F:** web-доставка (твой приоритет по ТЗ), уже наработанный AI-workflow, отсутствие кривой обучения нового движка/языка.
- **Ничьи:** террейн, стройка-паззлы, Blender-пайплайн.

---

## 💡 Рекомендация

Для этого конкретного проекта чаша весов не склоняется однозначно ни в одну сторону — сильные стороны Godot (vehicle physics) закрывают ровно главный риск ТЗ, а сильные стороны R3F (web-доставка, отсутствие кривой обучения) закрывают ровно то, что зафиксировано как приоритет платформы.

**Практический вариант — не выбирать заранее, а сделать маленький технический прототип на обоих:**
1. **R3F-версия:** машина едет по плоской земле с raycast-контроллером, лёгкий подъём/спуск. Замерить, сколько времени уходит на «нормально едет и не переворачивается».
2. **Godot-версия:** та же сцена на `VehicleBody3D`. Замерить то же самое.

Если разница по времени тюнинга ощутима (а вероятно, будет — Godot тут даёт готовый инструмент под именно эту задачу), это станет объективным аргументом в пользу Godot для **именно этого проекта**, не отменяя R3F как основной стек для всей остальной дорожной карты.

Не менять стек полностью, а рассматривать Godot как **параллельный трек для конкретных vehicle/dron-проектов**, где встроенная физика транспорта закрывает главный риск — раньше уже прозвучавший вывод остаётся в силе и после детального разбора по системам.
