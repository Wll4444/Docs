# Ревью Codex и реализация Claude Code

Пилот: Template и TinyWhoopPlayground. Claude Code реализует, Codex независимо
проверяет код, тесты и критерии приёмки; владелец принимает решения.
Первый этап — ревью. Подключение Blender и создание ассетов — отдельный второй этап.

## Как загружаются инструкции

Общий файл — `C:/Projects/Games/AGENTS.md`. В каждом участвующем репозитории
локальный `AGENTS.md` явно поручает его прочитать: автоматический поиск Codex
обычно начинается с корня Git, поэтому родительский файл может не загрузиться.
Локальные инструкции также поручают прочитать соответствующие `CLAUDE.md`.
Общие архитектурные правила остаются в существующих файлах, без второй копии.

Источники: [обнаружение AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md),
[локальное ревью](https://learn.chatgpt.com/docs/code-review?surface=app).

При первом чате проекта попросить Codex назвать прочитанные инструкции и его роль.
Ожидается общий AGENTS.md, общий CLAUDE.md, локальные файлы и правила игры.
Если общая папка недоступна, агент сообщает об этом; полный контекст не предполагается.
Для облачного ревью общий документ нужно предоставить внутри доступного репозитория.

Ограничение в AGENTS.md — инструкция агенту, а не настройка прав файловой системы.
Для дополнительного ограничения можно использовать режим доступа только для чтения;
запуск build, скриншотов и некоторых тестов при этом может требовать разрешения на запись.

## Передача работы на ревью

Когда запрашивать ревью: при закрытии этапа и после рискованных изменений — физика,
ввод, арм/failsafe, reset/generation, код, который уйдёт в Template. Правки, не
затрагивающие поведение, отдельного ревью не требуют: цена круга должна быть меньше цены
пропущенного дефекта.

1. Claude готовит небольшой завершённый diff, выполняет подходящие проверки и
   **фиксирует его коммитом** (чистый `git status`; для этапа — промежуточный тег
   `stage-NN-rc`). Отчёт со списком проверок и известных ограничений готов к передаче.
2. Владелец указывает репозиторий, этап, требования и точный scope: коммит или
   диапазон BASE..HEAD.
3. Ревью идёт по зафиксированному hash, а не по рабочему дереву: Claude может
   продолжать работу, не меняя рассматриваемый коммит. Незакоммиченные изменения —
   исключение: тогда Claude приостанавливает редактирование, а Codex записывает HEAD,
   статус, список файлов и проверяет, что diff не изменился к завершению.
   В scope записываются hash **коммитов**: для аннотированного тега
   `git rev-parse stage-NN^{commit}`, иначе получается hash объекта тега
   (TinyWhoop, круг 1 этапа 3).
4. Codex сначала читает требования, diff и вызываемый код, формирует собственные
   выводы, затем сверяет их с отчётом Claude и заявленными результатами проверок.
   Результат он записывает в [файл ревью](#файл-ревью) и кратко повторяет в чате.
5. Владелец читает **сводку** в начале файла, а подробности — только там, где
   нужно его решение. Решение обязательно для P1, P2 и замечаний, которые спорят
   с задокументированным решением: принять, отклонить, в долг или вариант. P3 без
   такого спора по умолчанию уходит в долг; строку «Владелец» под ним пишут, только
   чтобы это изменить. Затем владелец говорит чату Claude прочитать файл. Claude
   работает по замечаниям с решением владельца, P3 без решения переносит в долг и
   под каждым отвечает: исправлено с доказательством, отклонено с обоснованием
   или перенесено в долг.
6. Исправления идут отдельным коммитом; Codex проверяет `rc..HEAD` и необходимые
   связанные места и дописывает в тот же файл раздел второго круга. Если появились
   другие изменения, они явно включаются в новый scope.
7. Не больше двух кругов ревью на этап. P1 и P2 блокируют закрытие, пока не исправлены
   с доказательством или не отклонены владельцем с обоснованием. P3 по умолчанию
   уходит в реестр долга. Замечание, найденное только на втором круге, владелец
   вправе перенести в долг, а не открывать третий круг.
8. Claude закрывает этап по существующей процедуре: отчёт, реестр долга,
   коммит и тег. В отчёт этапа входит блок «Ревью Codex»: scope (hash и база),
   число замечаний по приоритетам, исход каждого (исправлено / отклонено / в долг),
   ссылка на файл ревью. Файл ревью Claude коммитит вместе с исправлениями или
   отчётом этапа.

Агенты не отправляют сообщения друг другу. Канал между ними — файл ревью, а
переход хода от одного к другому делает владелец, после своих решений в файле.
Согласие двух моделей не заменяет воспроизведение дефекта или измерение.

## Что проверяет Codex

- Поведение и критерии приёмки, включая переходы состояний и ошибочные входы.
- Физический шаг, FPS, единицы, силы/импульсы, координаты, reset и generation.
- React/R3F lifecycle, подписки, частые выделения памяти и освобождение ресурсов.
- Достоверность тестов, зондов и калибровки: видит ли проверка заявленный дефект.
- Применимость унаследованных правил и измерений к текущей игре.
- Для Template: переносимость изменений до включения в общий шаблон.
- Для TinyWhoop: реальный ввод, failsafe, арм, моторы и порядок физических операций.

Codex может запускать существующие проверки, создавать игнорируемые временные
результаты и писать [файл ревью](#файл-ревью), названный в запросе. Он не меняет исходники, зависимости и эталонные записи; не запускает
мутационные скрипты, которые временно переписывают исходники в рабочем дереве Claude.
Неустановленные зависимости и недоступные GPU/пульт отмечаются как ограничения.
Для визуальных утверждений нужно смотреть PNG, а не только код завершения команды.

**Отдельный checkout.** Если основной checkout ушёл с рассматриваемого коммита, Codex
проверяет в отдельном worktree на точном hash. `node_modules` можно подключить
junction-ссылкой на каталог основного checkout (это не установка пакетов), но уборка
worktree может пройти по ссылке и опустошить оригинал. Поэтому:

- до уборки worktree — и до конца ответа, если worktree убирает приложение, — удалить
  саму ссылку: `cmd /c rmdir <worktree>\node_modules` (без `/s`). Не рекурсивным
  удалением: `Remove-Item -Recurse` в Windows PowerShell 5.1 удаляет содержимое цели;
- затем проверить, что `node_modules/.bin/tsc` основного checkout на месте, и записать
  это в scope круга. Claude, начиная работу по файлу ревью, проверяет то же самое;
- свой `npm ci` в worktree — установка пакетов, только с разрешения владельца.

Пустой `node_modules` не всегда даёт ошибку: `npx tsc` идёт в сеть за чужим пакетом
`tsc`, `npx vitest run` выходит успешно без единого теста. Прогон засчитывается по числу
тестов в выводе, а не по коду завершения. Источник: TinyWhoop, круг 2 ревью L02a
(2026-10-20) — после проверки в worktree с junction `node_modules` основного checkout
оказался пуст, восстановлен `npm ci`; отчёт L02c, находка 4.

## Формат результата

Сначала scope: проект, этап, HEAD/BASE или коммит, список рассматриваемых изменений.
Для каждого замечания:

- ID и приоритет: P1 — блокирует приёмку этапа; P2 — существенная ошибка поведения;
  P3 — ограниченная проблема. Приоритет зависит от требований текущего этапа.
- Файл и точная строка.
- Входные данные или последовательность событий, вызывающая проблему.
- Как часто это случается в обычной игре: при каком FPS, вводе, действии игрока.
  Приоритет ставится по реалистичному случаю; худший случай указывается отдельно.
- Ожидаемое и фактическое поведение, последствия.
- Основание: воспроизведено / следует из кода / гипотеза.
- Если замечание спорит с задокументированным решением (правило, комментарий в коде,
  тест, план) — назвать это решение и где оно записано. Такое замечание решает
  владелец: исправить код или поправить правило.
- Способ проверить исправление.

Подтверждённые замечания и гипотезы идут отдельно. Проверки перечисляются с
результатами; отдельно — что не проверено. «Замечаний не найдено» означает результат
в указанном scope, а не гарантию исправности проекта.
Уроки и Inbox пополняются только по запросу, после проверки фактов.

## Файл ревью

Один файл на этап, в репозитории проекта:
`Docs/02_Journal/reviews/stage-NN-codex.md`. Его пишут трое, каждый в своём месте:

```markdown
# Ревью Codex — этап NN

## Круг 1 — scope BASE..HEAD (hash коммитов), дата

### Сводка для владельца
Не больше 10 строк — всё, что владельцу нужно прочитать:
- R1 [P2] одна фраза — **нужно решение**: А — …, Б — …; Codex советует А.
- R2 [P3] одна фраза — по умолчанию в долг.
Итог: P1 — 0, P2 — 1, P3 — 1; что не проверено одной строкой.

Дальше — для Claude и Codex: проверки, ограничения, подробности замечаний.

### R1 [P2] Краткое название
Поля из «Формата результата».
**Владелец:** принять / отклонить: почему / в долг / вариант А.
**Claude:** исправлено — коммит, тест или PNG / отклонено — почему / в долг D-NN.

## Круг 2 — scope rc..HEAD (hash), дата
По каждому R: подтверждено исправление или нет. Новые замечания — R-номера дальше.
```

- Codex создаёт файл и дописывает разделы кругов; чужие строки не правит.
- Владелец пишет только строки «Владелец», Claude — только строки «Claude».
- ID замечаний сквозные через круги: «R3» в коммите и отчёте этапа однозначен.
- Пока файл не закоммичен, он лежит в рабочем дереве Claude как неотслеживаемый —
  это единственный файл, который Codex в нём создаёт.

## Запрос ревью

```text
Проведи независимое ревью <проект>, <BASE>..<HEAD> (этап NN).
Сначала прочитай AGENTS.md и указанные им общие и проектные правила.
Не меняй исходники и не коммить. Единственный файл, который ты пишешь, —
Docs/02_Journal/reviews/stage-NN-codex.md, раздел «Круг 1».
Фокус: <что рискованно в этом этапе>.
Сначала сформируй выводы по коду, затем сверь их с отчётом Claude.
```

Перед запуском проверить, что BASE и HEAD существуют; scope записывается
разрешёнными hash. Запрос Claude после решений владельца:
«Прочитай Docs/02_Journal/reviews/stage-NN-codex.md; работай по замечаниям с решением
владельца; ответь строкой „Claude“ под каждым; исправления — отдельным коммитом».

Автоматический вызов Codex из Claude (`codex exec`, Codex как MCP-сервер) возможен,
но убирает решение владельца между кругами. Рассматривать после пилота, если ручной
переход хода окажется узким местом.

## Как оценивать пилот

Решение, оставлять ли схему и переносить ли её в другие проекты, принимается после
2–3 этапов по числам, а не по впечатлению. Для каждого этапа в блоке «Ревью Codex»
(или в заметке владельца) фиксируются:

- подтверждённые P1/P2, найденные Codex и не найденные Claude;
- ложные срабатывания и гипотезы, не подтвердившиеся;
- дефекты, которые нашлись позже и Codex их пропустил.

Дефекты, найденные и исправленные внутри этапа, для калибровки не годятся: в итоговом
diff их уже нет. Пропуски Codex видны только по дефектам, найденным после его ревью.

Первый круг (TinyWhoop stage-02..stage-03, 2026-10-06): 3 замечания, все подтвердились
по сути; два Claude не видел, одно опровергло пункт его отчёта (кадрирование hover);
у одного приоритет завышен по худшему случаю (журнал полёта, P2 → P3). Отсюда поля
«как часто» и «спорит с решением» в формате результата.

Круг 2 (2026-10-07, исправления `f2f03e2..a4d9083`): R1 — пробел в правиле безопасности
(защёлка газа после возврата пульта) — владелец выбрал вариант А, Claude исправил с
мутацией M13, Codex подтвердил, владелец проверил на настоящем Pocket. R2 и R3 ушли в
долг (D-15, D-16). Новых замечаний нет. Главная цена цикла — время владельца на чтение
138 строк файла ради одного решения; отсюда сводка для владельца и P3 в долг по умолчанию.
Источник: TinyWhoopPlayground, `Docs/02_Journal/reviews/stage-03-codex.md`, коммит `b9db480`.

Итог пилота — урок в `04_Lessons`.

## Второй этап: Blender

В этом пилоте MCP-настройки, сцены и ассеты не меняются. Отдельная задача второго
этапа — проверить уже установленный сервер, подключить его к Codex и согласовать
порядок работы с Blender, исходники ассетов и проверку экспорта в R3F.
