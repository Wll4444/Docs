# 🤖 Godot + AI Stack Cheat Sheet

Справочник по связке Godot Engine и AI-ассистента (Claude Code / Claude Desktop) через MCP.
Параллельная ветка к `web_game_dev_stack.md` — для оценки Godot как альтернативы/дополнения
к R3F-стеку для 3D web/mobile/PC проектов.

---

## 🏗️ 1. Ядро (The Engine)

* **[Godot 4.x](https://godotengine.org/)** — открытый движок, узел-ориентированная архитектура (Scene Tree),
  свой язык GDScript (или C# при желании). В отличие от Three.js/R3F — не библиотека поверх веб-платформы,
  а полноценный редактор с собственным рантаймом, который экспортируется на разные платформы.
* **Renderer:** Forward+ (десктоп/консоли) или Mobile-режим — для web/mobile-экспорта стоит сразу
  проверять, какой рендер-профиль используется, т.к. это влияет на доступные шейдеры и производительность.
* **Экспорт-платформы:** Web (HTML5/WebAssembly), Android, iOS, Windows/Linux/macOS — единая кодовая база,
  в отличие от R3F, где web — единственная целевая платформа "из коробки" (mobile/desktop требуют
  обёртки типа Capacitor/Tauri).

## ⚙️ 2. Физика (Physics)

* **Godot Physics** — встроенный движок, не требует отдельной интеграции (в отличие от Rapier в R3F-стеке).
  * **RigidBody3D / CharacterBody3D / StaticBody3D** — аналоги подходов из Rapier, но нативно завязаны на Scene Tree.
  * **Area3D** — триггер-зоны для коллизий без физического отклика (детект попаданий, разрушение объектов).
  * Плюс: меньше boilerplate, физика "просто работает" без настройки моста.
  * Минус: меньше контроля на низком уровне, чем в Rapier/WASM.

## 🧠 3. AI-ассистирование через MCP

MCP-сервер даёт AI-ассистенту видимость сцены/скриптов/дебаггера, вместо слепой генерации кода в чат.

| Сервер | Тип | Стоимость | Особенность |
|---|---|---|---|
| **GDAI MCP** | File-level | $19 разово | Самая полная документация, closed-loop отладка (правка → запуск → скриншот-проверка) |
| **Coding-Solo/godot-mcp** | File-level | Бесплатно, open-source | Хорошая стартовая точка, меньше edge-кейсов покрыто |
| **ee0pdt/Godot-MCP** | File-level | Бесплатно, open-source | Похож на Coding-Solo |
| **Summer Engine** | Engine-level | Хостится (уточнять тариф) | Живой мост к запущенному движку — дебаггер и рантайм в реальном времени |
| **StraySpark Godot MCP** | File-level | Коммерческий | Курируемый набор тулов |
| **godot-dap-mcp-server** | Engine-level (debug) | Бесплатно, в разработке | Пошаговая отладка через Debug Adapter Protocol (брейкпоинты, степы) |

**File-level vs Engine-level:** file-level серверы читают/пишут `.tscn`/`.gd` как текст и общаются с
редактором через плагин — этого достаточно для 90% задач кодинга. Engine-level серверы держат мост
к реально запущенному инстансу движка — агент может создавать ноды в живом дереве, читать рантайм-ошибки
во время игры, самостоятельно перезапускать и проверять результат.

## 🎨 4. AI за пределами кодогенерации

* **Скриншот-верификация** — часть MCP-серверов (GDAI, Summer Engine) умеет делать скриншоты редактора
  и запущенной игры, чтобы агент "видел" визуальный результат своих правок, а не только текст ошибок.
* **Blender MCP + Godot MCP в одной сессии** — уже знакомый тебе паттерн: смоделировать проп в Blender →
  экспорт в glTF → импорт в Godot через MCP → настройка import-параметров → добавление в сцену.
  Тот же end-to-end пайплайн, что ты уже опробовал на 3D-доме, просто с Godot вместо чистого R3F-проекта.
* **Симуляция ввода** — некоторые серверы умеют эмулировать нажатия клавиш/actions в запущенной игре,
  что полезно для автоматического плейтеста простых механик (например, отскок шара в Krakout).

## 🕹️ 5. Игровая логика и инструменты

* **Autoload (Singleton)** — аналог Zustand-стора: глобальный скрипт-нода, доступная из любой сцены,
  для хранения состояния игры (счёт, жизни, MENU/PLAYING/GAMEOVER).
* **Signals** — встроенная система событий Godot (аналог `onClick`/`event.stopPropagation()` в R3F,
  но объявляется декларативно в редакторе или через `emit_signal`).
* **Resource-файлы (.tres)** — переиспользуемые данные (например, набор цветов блоков), аналог
  вынесенных констант/конфигов в JS-стеке.

## 🛠️ Архитектурные паттерны при работе с AI-ассистентом

1. **Инкрементальное построение сцены** — как и в Blender-workflow, лучше просить агента собирать
   сцену по частям (сначала статичные объекты, потом физика, потом UI), а не одним большим скриптом.
2. **Явно указывать целевой MCP-сервер**, если подключено несколько (`используй godot-summer для этого`) —
   особенно при переключении между file-level и engine-level в рамках одного пилота.
3. **Просить скриншот-проверку после ключевых шагов** — там, где сервер это поддерживает, это заметно
   снижает число "агент думает, что починил, а на самом деле нет".
4. **Не держать два MCP-сервера подключёнными к одному запущенному редактору одновременно** —
   возможны конфликты порта/соединения (см. отдельное обсуждение).

## 📝 Заметки для сравнения с R3F-стеком

- [ ] Оценить, насколько GDScript-ошибки (слабая типизация) увеличивают число неудачных попыток агента.
- [ ] Замерить размер и время загрузки web-билда (HTML5-экспорт) на пилотном проекте.
- [ ] Сравнить субъективную скорость итерации: сцена-редактор (Godot) vs декларативный JSX (R3F).
- [ ] Проверить, насколько безболезненно один и тот же проект идёт на Android/desktop без доп. обёрток.
